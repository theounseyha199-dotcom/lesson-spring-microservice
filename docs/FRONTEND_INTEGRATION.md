# Frontend integration guide

This guide describes the current controllers, DTOs, validation, and persistence behavior in this repository. It covers all four services. Example IDs and timestamps below are illustrative. Actual IDs are generated by the backend.

## 1. Start the backend

Run commands from the repository root. The Gradle build requires a Java 25 toolchain; check your local Gradle Java configuration if compilation reports that it is missing.

Create the external Docker network once if it does not already exist:

```bash
docker network create ite-net
docker compose -f deployment/docker-compose.yaml up -d postgres mongodb
```

Run each service in its own terminal:

```bash
./gradlew -p microservices/customer-service :customer-service-main:bootRun
./gradlew -p microservices/business-service :business-service-main:bootRun
./gradlew -p microservices/order-service :order-service-main:bootRun
./gradlew -p microservices/payment-service :payment-service-main:bootRun
```

For a customer-only frontend, start MongoDB and the customer service; the other services are not needed for customer operations.

| Service | Default HTTP origin | Port override | Storage |
| --- | --- | --- | --- |
| Customer | `http://localhost:8084` | `CUSTOMER_PORT` | MongoDB `istad_customer` |
| Business | `http://localhost:8082` | `BUSINESS_PORT` | MongoDB `istad_business` |
| Order | `http://localhost:8081` | `ORDER_PORT` | PostgreSQL `istad_order` |
| Payment | `http://localhost:8083` | `PAYMENT_PORT` | MongoDB `istad_payment` |

These are backend server addresses, not database connection URLs. The frontend sends HTTP requests to the services; MongoDB and PostgreSQL credentials do not belong in frontend configuration. There is no API gateway in the current project.

## 2. Browser access and authentication

The project currently has no configured API authentication, login endpoint, bearer token requirement, or browser CORS policy. Send no database credentials, `Authorization` header, or credential cookies. `SYSTEM` audit values come from backend configuration and do not identify a signed-in frontend user.

A browser page on `http://localhost:3000` calling `http://localhost:8084` directly is cross-origin. JSON POST, PUT, and DELETE requests need preflight approval, which the current backend does not configure. A working curl or Postman request does not establish browser access.

Use a same-origin frontend development proxy or reverse proxy. Configure these routes, preserving the `/api/...` part and removing only the frontend prefix:

| Browser prefix | Backend target | Example |
| --- | --- | --- |
| `/backend/customer` | `http://localhost:8084` | `/backend/customer/api/customers` → `http://localhost:8084/api/customers` |
| `/backend/business` | `http://localhost:8082` | `/backend/business/api/businesses` → `http://localhost:8082/api/businesses` |
| `/backend/order` | `http://localhost:8081` | `/backend/order/api/orders` → `http://localhost:8081/api/orders` |
| `/backend/payment` | `http://localhost:8083` | `/backend/payment/api/payments` → `http://localhost:8083/api/payments` |

For example, the following Nginx server serves a built SPA and forwards API requests. Replace `/absolute/path/to/frontend/dist` with your frontend build directory. This is an example configuration to add to your local Nginx setup; it is not installed by this repository.

```nginx
server {
    listen 3000;
    server_name localhost;
    root /absolute/path/to/frontend/dist;
    index index.html;

    location /backend/customer/ {
        proxy_pass http://127.0.0.1:8084/;
    }
    location /backend/business/ {
        proxy_pass http://127.0.0.1:8082/;
    }
    location /backend/order/ {
        proxy_pass http://127.0.0.1:8081/;
    }
    location /backend/payment/ {
        proxy_pass http://127.0.0.1:8083/;
    }
    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

Open the frontend through `http://localhost:3000`. The trailing slash in each `proxy_pass` replaces the matching `/backend/SERVICE/` prefix with `/`. If the proxy itself runs in a container, `127.0.0.1` points to that container; configure the backend targets for your deployment instead.

Alternatively, configure explicit allowed frontend origins on each backend service before using direct browser URLs. Adding CORS is a separate backend change; changing the Fetch `mode` to `no-cors` will not make JSON API integration work.

## 3. Endpoint map

Paths below are backend paths, before adding the frontend proxy prefix.

| Service | Method | Path | Success | Purpose |
| --- | --- | --- | --- | --- |
| Customer | GET | `/api/customers` | 200 + array | Filtered page of active and inactive customers |
| Customer | GET | `/api/customers/{customerId}` | 200 + object | Read customer |
| Customer | GET | `/api/customers/statistics` or `/statistics` | 200 + object | Counts by status, segment, and both |
| Customer | PATCH | `/api/customers/{customerId}/status` | 200 + object | Set ACTIVE or INACTIVE |
| Customer | PUT / DELETE | `/api/customers/{customerId}/segment` | 200 + object | Assign an active segment / clear membership |
| Segment | GET / POST | `/api/customer-segments` | 200 + array / 201 + object | Filtered list / create |
| Segment | GET / PUT / DELETE | `/api/customer-segments/{segmentId}` | 200 / 200 / 204 | Read / update / soft delete |
| Customer | POST | `/api/customers` | 201 + object | Create customer |
| Customer | PUT | `/api/customers/{customerId}` | 200 + object | Update names and optional contact fields |
| Customer | PUT | `/api/customers/{customerId}/deactivate` | 200 + event | Set an active customer to inactive |
| Customer | DELETE | `/api/customers/{customerId}` | 204 + no body | Mark customer deleted |
| Business | POST | `/api/businesses` | 201 + object | Create business |
| Order | POST | `/api/orders` | 201 + object | Create pending order |
| Payment | POST | `/api/payments` | 201 + object | Register pending payment |

There is no customer GET-by-ID endpoint, search, pagination, restore, or activate endpoint. Business, order, and payment currently expose creation only: no list, detail, update, delete, or payment-completion HTTP endpoints. Domain methods are not automatically HTTP endpoints.

Send `Content-Type: application/json` when sending JSON. UUIDs are strings. Monetary values are JSON numbers; the backend uses `BigDecimal`. Timestamps are date strings. Successful responses have no common `{data: ...}` wrapper: read the returned object or array directly.

## 4. Customer API

See the [Customer service README](../microservices/customer-service/README.md) for complete Segment CRUD, business rules, filtering syntax, statistics examples, and integration-test commands.

Customer and segment lists default to page 0, size 20. Supply `page`, `size` (1..100), `sort`, `direction`, `search`, and repeated `filter=field:operator:value` parameters. The TypeScript client's `customers.list(options, signal)` and `segments.list(options, signal)` accept these options. Examples:

```ts
const customers = await api.customers.list({ filters: ["status:eq:ACTIVE"], page: 0, size: 20 });
const segments = await api.segments.list({ search: "VIP" });
const statistics = await api.customers.statistics({ filters: ["status:eq:ACTIVE"] });
```

Segment bodies use `{ name, description? }` for create and `{ name, description?, status }` for update. Only ACTIVE segments accept assignments. Deleting a segment preserves existing customer memberships for statistics and prevents new assignments. Counts exclude deleted customers; `segmentId: null` represents unassigned customers. Statistics always count all matching customers, independently of list pagination.


### Create

`POST /api/customers`

```json
{
  "username": "sokha",
  "familyName": "Chan",
  "givenName": "Sokha",
  "email": "sokha@example.com",
  "phoneNumber": "+85512345678"
}
```

All five contact fields are required. Names and username are limited to 100 characters; email must be valid; phone must contain 8 to 15 digits with an optional `+` prefix. Username and email are normalized to lowercase and are unique among nondeleted customers. An optional `segmentId` UUID assigns an ACTIVE segment. Duplicate identities return 409. Creation responses also include `segmentId` (null when unassigned).

`201 Created`:

```json
{
  "customerId": "11111111-1111-1111-1111-111111111111",
  "username": "sokha",
  "familyName": "Chan",
  "givenName": "Sokha",
  "email": "sokha@example.com",
  "phoneNumber": "+85512345678"
}
```

The backend sets the initial status to `ACTIVE`, but the creation response omits status and audit fields. Reload the customer list to obtain the current status.

### List

`GET /api/customers` returns `200 OK`:

```json
[
  {
    "customerId": "11111111-1111-1111-1111-111111111111",
    "username": "sokha",
    "familyName": "Chan",
    "givenName": "Sokha",
    "email": "sokha@example.com",
    "phoneNumber": "+85512345678",
    "status": "ACTIVE"
  }
]
```

An empty list is `[]`. The response is not paginated and has no guaranteed sort order. Sort/filter locally for a small dataset. Deleted customers are excluded; inactive customers remain visible. Audit fields stored in MongoDB are not exposed by this response.

### Update customer details

`PUT /api/customers/{customerId}`

```json
{
  "familyName": "Chan",
  "givenName": "Sokha Updated"
}
```

Both names are required and nonblank. Optional `username`, `email`, and `phoneNumber` fields update contact details. It returns `200 OK` with the flat six-field contact response. Use `GET /api/customers/{customerId}` for status and segment membership. Missing or deleted customer: `404`; invalid input: `400`; duplicate identity or concurrent edit: `409`. Inactive customers can still be updated. Use `PATCH /api/customers/{customerId}/status` with `{ "status": "ACTIVE" }` or `INACTIVE` for status transitions.

### Deactivate

`PUT /api/customers/{customerId}/deactivate` has no request body.

The current response is a domain event rather than a flat customer DTO. Its `customer` contains nested ID, email, and phone values:

```json
{
  "customer": {
    "id": { "value": "11111111-1111-1111-1111-111111111111" },
    "username": "sokha",
    "familyName": "Chan",
    "givenName": "Sokha",
    "email": { "value": "sokha@example.com" },
    "phoneNumber": { "value": "+85512345678" },
    "status": "INACTIVE"
  },
  "initiatedAt": "2026-10-19T08:00:00Z"
}
```

The timestamp formatting can include a zone offset or zone information. Treat it as a date string. Reload the list for the standard flat customer shape. Already inactive: `409 Conflict`. Missing or deleted: `404`. There is no reactivation endpoint.

### Delete

`DELETE /api/customers/{customerId}` has no request body.

On success, `204 No Content` has no JSON body. Do not call `response.json()` unconditionally.

The backend retains the MongoDB document, sets status to `DELETED`, records `deletedAt` and `deletedBy`, and refreshes modification details. Creation details remain intact. The auditor is currently `SYSTEM`. Both active and inactive customers can be deleted. A second delete, or a missing customer, returns `404`.

Remove the row from local state after success or reload the list. There is no restore endpoint. Keep deactivate and delete as distinct frontend actions.

## 5. Business API

`POST /api/businesses`

```json
{
  "name": "Sokha Market",
  "email": "hello@sokhamarket.example",
  "address": "Phnom Penh"
}
```

Name/address must be nonblank; email must be present and valid. `201 Created`:

```json
{
  "businessId": "22222222-2222-2222-2222-222222222222",
  "name": "Sokha Market",
  "email": "hello@sokhamarket.example",
  "address": "Phnom Penh",
  "status": "ACTIVE",
  "createdAt": "2026-10-19T08:00:00Z"
}
```

Retain the returned `businessId` for order creation. There is no business listing endpoint to repopulate a selector after a page reload.

## 6. Order API

`POST /api/orders`

```json
{
  "customerId": "11111111-1111-1111-1111-111111111111",
  "businessId": "22222222-2222-2222-2222-222222222222",
  "deliveryAddress": "Phnom Penh",
  "items": [
    {
      "productId": "33333333-3333-3333-3333-333333333333",
      "quantity": 2,
      "unitPrice": 5.00
    }
  ]
}
```

Customer, business, and product IDs must be UUIDs. Address is required. Include at least one item; each needs integer `quantity >= 1` and `unitPrice >= 0.01`. There is no product catalog API in this project; product IDs and prices must come from your application inputs or fixtures.

`201 Created`:

```json
{
  "orderId": "44444444-4444-4444-4444-444444444444",
  "customerId": "11111111-1111-1111-1111-111111111111",
  "businessId": "22222222-2222-2222-2222-222222222222",
  "total": 10.00,
  "status": "PENDING",
  "createdAt": "2026-10-19T08:00:00Z"
}
```

The backend calculates `total = sum(quantity × unitPrice)`. Use the returned total as the order total. The response does not contain items or delivery address; retain submitted data if displaying those in the current session. The backend accepts caller-supplied prices and does not verify product/customer/business existence across services.

## 7. Payment API

`POST /api/payments`

```json
{
  "orderId": "44444444-4444-4444-4444-444444444444",
  "customerId": "11111111-1111-1111-1111-111111111111",
  "amount": 10.00
}
```

IDs must be UUIDs; amount must be at least `0.01`. `201 Created`:

```json
{
  "paymentId": "55555555-5555-5555-5555-555555555555",
  "orderId": "44444444-4444-4444-4444-444444444444",
  "customerId": "11111111-1111-1111-1111-111111111111",
  "amount": 10.00,
  "status": "PENDING",
  "createdAt": "2026-10-19T08:00:00Z"
}
```

This registers a pending payment. It does not charge a card, redirect to a payment provider, confirm settlement, or mark an order paid. There is no payment completion/polling endpoint. Show “Payment registered” rather than “Payment completed.” No currency is defined in the current request/response contract. The backend does not verify that the amount matches the referenced order or prevent duplicate payment registrations.

## 8. TypeScript client and error handling

Copy [api-client.ts](frontend/api-client.ts) into your frontend. It uses native Fetch, takes configurable service base URLs, handles empty responses, and exports request/response types for all eight endpoints. Its types describe compile-time expectations; it does not perform runtime schema validation.

The default base URLs use the proxy prefixes in section 2:

```ts
import { createFrontendApi, ApiError } from "./api-client";

const api = createFrontendApi();

try {
  await api.customers.create({
    username: "sokha",
    familyName: "Chan",
    givenName: "Sokha",
    email: "sokha@example.com",
    phoneNumber: "+85512345678",
  });
  const customers = await api.customers.list();
  console.log(customers);
} catch (error) {
  if (error instanceof ApiError) {
    console.error(error.status, error.message);
  } else {
    // Network/CORS/proxy failure or an unexpected response.
    console.error(error);
  }
}
```

After configuring CORS, server-side code or a browser can instead inject direct origins:

```ts
const api = createFrontendApi({
  customer: "http://localhost:8084",
  business: "http://localhost:8082",
  order: "http://localhost:8081",
  payment: "http://localhost:8083",
});
```

Server-side HTTP clients do not need browser CORS approval. In deployed frontends, `localhost` means the user's machine, so configure deployed addresses or keep the same-origin proxy prefixes.

| Situation | HTTP status | Frontend handling |
| --- | --- | --- |
| Invalid fields, malformed JSON, invalid UUID | 400 | Keep entered data and show validation feedback |
| Missing/deleted customer or repeated delete | 404 | Refresh the list and remove stale selections |
| Deactivating an inactive customer | 409 | Refresh status and explain the conflict |
| Backend/database failure | Usually 5xx | Keep form state and allow the user to retry deliberately |
| Network, proxy, or browser CORS failure | No readable HTTP response | Check service/proxy availability and browser console |

Business, order, and payment custom validation handlers return an object such as `{"error":"Invalid order request"}` for handled validation failures. Customer errors return Problem Details JSON with a readable `detail`, including 400 validation/filter errors, 404 missing resources, and 409 uniqueness/lifecycle/concurrent-edit conflicts. Other Spring errors may use a different default shape; do not assume every error contains `error` or field-level details. The client checks the status and safely reads JSON, plain text, or an empty body.

Do not automatically retry POST requests: a lost response may have followed a successful insert, and there are no idempotency keys. Disable repeated submit clicks while a request is pending. The sample client does not retry automatically or send credentials.

## 9. Suggested frontend flows

### Customer management

1. Load `api.customers.list()` and render loading, empty, success, and error states.
2. Use `customerId` as the row key; keep phone numbers as strings to retain `+` and leading zeroes.
3. Create using the five editable fields. Reload the list after success.
4. Edit names and optional contact fields, then reload the current filtered page.
5. Enable deactivate for `ACTIVE` rows. After success, reload the list to show `INACTIVE`.
6. Confirm delete, call `api.customers.remove(id)`, and remove/reload the row after `204`.

There are no audit timestamps in the customer API responses, so a frontend audit-history screen needs an additional backend contract. Deactivation's event timestamp is not the customer creation timestamp.

### Customer → business → order → payment

```ts
const customer = await api.customers.create({
  username: "dara", familyName: "Sok", givenName: "Dara",
  email: "dara@example.com", phoneNumber: "+85512345678",
});
const business = await api.businesses.create({
  name: "Dara Market", email: "hello@daramarket.example", address: "Phnom Penh",
});
const order = await api.orders.create({
  customerId: customer.customerId,
  businessId: business.businessId,
  deliveryAddress: "Phnom Penh",
  items: [{ productId: "33333333-3333-3333-3333-333333333333", quantity: 2, unitPrice: 5 }],
});
const payment = await api.payments.create({
  orderId: order.orderId, customerId: customer.customerId, amount: order.total,
});
// payment.status is PENDING; this is not proof of payment completion.
```

The services do not coordinate a transaction. If payment registration fails, the customer/business/order may already exist. Keep returned IDs and retry only the operation that needs attention. Customer deletion does not cascade to existing orders/payments. Prevent selecting inactive/deleted customers in your UI if that is a business rule; order/payment services do not currently enforce it.

## 10. Verification and source references

Run the customer tests and package the service:

```bash
./gradlew -p microservices/customer-service test :customer-service-main:bootJar
```

The customer tests cover query JSON, delete status codes, repository mapping/filtering, and auditing behavior with mocked database operations. They do not prove a running database connection or a browser proxy setup. With the backend running, verify the list directly and through your proxy:

```bash
curl -i http://localhost:8084/api/customers
curl -i http://localhost:3000/backend/customer/api/customers
```

Both should return a JSON array. Check the browser Network panel for the same proxied request, particularly after writes. A proxy route returning the SPA's HTML means the API forwarding path needs correction.
